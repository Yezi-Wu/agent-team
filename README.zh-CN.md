# Agent Team

[English](README.md) | [中文说明](README.zh-CN.md)

**Agent Team** 是一个用于设计和协调多 Agent 工作流的通用 Skill。你只需要给出目标，它会根据场景设计合适的团队分工、明确交接、建立共享工作区、记录过程，并启用独立审核与返工闭环。

它是“架构与协作规则”，不是 MCP 服务、模型服务或绑定某个平台的运行系统。Codex、Claude Code、Cursor 或其他支持 Skill 的 AI 宿主，负责提供模型、工具、文件访问与任务执行能力。

## 能做什么

- 将一个目标拆成能力地图，并设计最小但够用的 Agent 团队。
- 根据场景生成角色，不强制每个项目都必须有产品、设计、工程等固定岗位。
- 默认使用闭环：**规划 → 专业执行 → 独立审核 → 定向返工 → 复核 → 交付**。
- 总控 Agent 是固定角色，负责所有调度、状态和 Agent 间交接。
- 将需要长期保存的协作文档统一放入 `Agent work/`，每个 Agent 独立目录，流程、注册表和记录放在共享目录。
- 当宿主支持创建多个任务窗口时，创建可见的角色任务，并按照文档进行交接。
- 发布、花钱、部署、操作真实账号等不可逆外部行为始终需要你确认。

## 自动协作模式

每个任务开始时，总控会自动选择“够用且安全”的协作强度，并把原因记录到 `Agent work/dashboard.md`。你不需要每次手动选择；如有需要，也可以直接说“快速模式”“标准模式”或“严格模式”覆盖它的判断。

| 模式 | 典型场景 | 工作方式 |
| --- | --- | --- |
| **快速** | 低风险、容易撤销的简单结果 | 分配 → 立即执行 → 交付；不做例行回执或独立审核。 |
| **标准** | 普通的多 Agent 协作，存在上下游依赖 | 核对输入后在同一轮直接执行；最后独立审核一次；不通过则定向返工一次。 |
| **严格** | 发布、部署、花钱、敏感数据、不可逆操作或错误代价高 | 先回执并由总控放行，再进行受控执行；关键阶段审核，记录更完整；不可逆操作前必须由你确认。 |

Skill 遇到外部或不可逆操作会自动选“严格”；只有简单低风险任务才选“快速”；其余默认“标准”。这样既不会为了形式反复沟通，也能保证重要任务有足够检查。

## 执行与用户决策卡

“准备好了”“已分析”“已理解”都不是任务完成状态。输入完整时，Agent 必须直接执行，并且只能以以下四种状态结束：

- `DONE`：给出精确产出路径和执行证据。
- `BLOCKED`：说明缺少的文件、事实、权限或其他具体阻塞项，以及恢复执行所需内容。
- `NEEDS-DECISION`：给你一张简短决策卡，包含问题、选项、各选项影响、受影响任务和你需要回复的内容。
- `FAILED`：说明失败的工具或动作、实际错误、影响和恢复建议。

总控会先核对所述产出后才接受 `DONE`。只有分析、没有产出的回复会被判为“未交付”，总控会补催一次，绝不会静默视为完成。需要你决定时，不相关任务继续；只有依赖该决定的任务暂停。

## 适合什么场景

当任务包含多个相互依赖的环节、需要独立审核，或需要清晰责任归属时，适合使用 Agent Team。例如：软件开发、自媒体运营、市场调研、招聘、学习规划等。

如果只是一个简单的一步任务，直接使用单个 Agent 通常更快、更清楚，不必强行拆成多 Agent。

## 核心工作方式

```text
用户目标
  ↓
总控：明确结果与验收标准
  ↓
规划角色 + 专业执行角色：完成领域工作
  ↓
独立审核角色：根据验收标准检查结果
  ↓
不通过 → 定向返工 → 复核一次
通过 → 交付并记录
```

审核角色必须独立于产出角色。执行 Agent 只提交指定产物和执行证据，不做重复的验收自检。在软件场景中，审核角色通常叫 QA；在其他场景中，可能叫编辑审核、事实核查、合规审核或学习评审。

## 场景示例

| 场景 | 规划角色 | 专业执行角色 | 独立审核角色 |
| --- | --- | --- | --- |
| 软件开发 | 产品 Agent | 设计、工程 | QA Agent |
| 自媒体账号 | 内容策略 Agent | 热点研究、文案、视觉 | 编辑 / 数据审核 Agent |
| 市场调研 | 调研负责人 | 资料研究、数据分析 | 事实核查 Agent |
| 招聘 | 招聘负责人 | 候选人搜寻、简历筛选、面试支持 | 合规审核 Agent |
| 学习计划 | 学习规划 Agent | 资料研究、课程设计 | 学习评审 Agent |

## 在 Codex 中快速开始

1. Clone 或下载本仓库。
2. 将 `agent-team` 文件夹放到 Codex 可识别的 Skill 目录。常见位置是：

   ```text
   C:\Users\<你的用户名>\.codex\skills\agent-team
   ```

   也可以把源文件放在其他盘，再建立一个目录链接到这个位置。
3. 在你希望执行项目的目录中，新建一个 Codex 任务。
4. 调用 Skill。当前这个项目对话会直接成为总控，Agent Team 不会额外创建总控窗口：

   ```text
   使用 $agent-team，帮我为一个自媒体账号创建多 Agent 体系。
   ```

5. 告诉它你的目标。Skill 会选择合适角色，为长期文档建立 `Agent work/` 工作区，并默认启用审核与返工闭环。

### 软件开发示例

```text
使用 $agent-team，在当前项目中开发一个任务管理 Web 应用。
```

它可以建立产品、设计、工程、QA 的协作流程：

```text
产品需求 + 验收标准
  → 设计规范
  → 工程实现 + 自检
  → QA 按验收标准测试
  → 不通过：工程修复 → QA 复测
  → 通过：总控汇总
```

### 自媒体示例

```text
使用 $agent-team，帮我创建一个面向职场新人的小红书账号多 Agent 体系。
```

系统通常会建立内容策略、热点研究、内容创作、编辑审核等角色。任何真实发布动作都必须由你确认。

## 自动生成的工作区

只要任务需要创建团队或保存长期产物，Agent Team 会在你选定项目根目录建立：

```text
Agent work/
├── README.md
├── dashboard.md             # 总控维护的全部 Agent 工作总览
├── deliverables/            # 仅放已确认、面向用户的交付物
│   ├── index.md
│   └── final-summary.md
├── shared/
│   ├── registry.yaml       # 当前角色与能力
│   ├── workflow.yaml       # 交接、审批与失败处理规则
│   └── trace.md            # 决策与完成的交接记录
├── <角色 1>/
│   └── ...
├── <角色 2>/
│   └── ...
└── <审核角色>/
    └── ...
```

软件团队通常会使用 `product/`、`designer/`、`engineer/`、`qa/`；其他场景会使用对应领域的角色名称。

想查看所有 Agent 的工作时，打开 `Agent work/dashboard.md`：里面会列出当前任务、状态、最新产物、审核结果、阻塞项和下一步。只想查看最终已确认的产出时，打开 `Agent work/deliverables/index.md`。

### 在主对话看产出，但不塞满总控上下文

子 Agent 的完整工作保存在文件中。总控在主对话只展示简短“交付卡片”：产物名称、状态、一两句事实摘要和文件路径，而不会复制整段子 Agent 回复。你需要完整内容时，再打开对应文件。这样主对话仍然清楚，也能减少重复上下文。

## 协作规则

- 每项能力只有一个明确的责任角色。
- 总控是唯一能够分配或改变任务的角色。
- Agent 使用精简、结构化的文件交接：交接编号、精确输入及版本、输出、标准、约束、状态和证据。
- 快速模式直接执行；标准模式可以确认输入，但必须在同一轮执行；严格模式仅在需要总控明确放行时单独回执。
- 专业执行角色不能私自改写上游需求。
- 审核角色依据总控维护的验收标准检查，而不是依据执行者自己的理解。
- 需求变更、角色冲突、风险动作或反复失败，会交由你决策。
- 多个 Agent 不应同时修改同一个文件。

## 最小上下文读取

多个 Agent 使用同一个项目目录，并不代表它们应该读取整个项目。Agent Team 默认采用“最小上下文”规则：

- 总控只在调度或需要决策时读取相关文件。
- 每个子 Agent 都会收到精简任务包，里面只列出允许读取的精确路径和预期输出。
- 子 Agent 不扫描整个仓库，也不读取无关文件；缺资料时，向总控申请一个明确的文件路径或事实。

这些规则会记录在 `Agent work/shared/context/`：`project-map.md` 只记录已发现且相关的文件；`task-packets/` 为每个 Agent 任务保存一份短任务包。

这是一条工作流规则，不是强制的系统安全权限。若需要真正隔离文件访问，请使用宿主提供的独立 worktree 或沙箱任务能力。

## 已确认版本与回滚

Agent Team 只会在你明确说“确认版本”“保存版本”或“发布版本”后记录版本。每个已确认版本都会在 `Agent work/shared/versions/` 中保存交付物清单、范围、时间和回滚依据。

- **Git 项目：** 已确认范围会获得独立提交和标签。
- **非 Git 项目：** 会保存已确认交付物与明确改动文件的带日期快照。
- **回滚：** 总控先告诉你目标版本和会影响的文件；你确认后，它先保存当前状态作为安全检查点，再恢复选定版本，并保留完整历史。

确认版本后，只有 `Agent work/.tmp/` 内的临时文件会自动删除。其他可能不再需要的文档会列在 `cleanup-candidates.md`，由你决定归档还是删除。

## 边界

Agent Team **不包含** MCP 服务、外部平台连接器、模型额度或后台自动化平台；这些由你使用的 AI 宿主提供。

当前项目对话会直接成为总控。如果宿主支持多个任务窗口，Skill 只创建需要的专业执行和审核 Agent，并由总控协调消息交接；如果不支持，也可以在当前任务中按同样的流程顺序完成。
